# How the Claude Code team does code review

著者は Addy Osmani、Morgan Westlee Lunt、Qing Wang。読了目安14分。fingerprint は取得した HTML 全体（curl）の sha256。

## 要点

- Claude Code チームのレビュー運用の紹介。Claude が Claude Code のコードの約90%を書くため、レビューの大半を機械に移し、人間の時間と注意を節約する方針を取った。
- 目標は、ほとんどの PR を「人間は最大1人（著者でもよい）」でマージしつつ、差し戻し（revert）やインシデントを増やさないこと。revert 率とインシデント率はガードレール。
- 変更は複数の層（作業時の検証、必須 CI、AI レビュー、セキュリティレビュー、リスク別の人間の承認、マージキュー、フラグと段階リリース、高速ロールバック）を通る。
- リスク分類器が承認の段階（不要・1人・2人）を決める。エージェントの承認は人間の承認の代わりにならない。
- レビュアーの改善ループ: 過去のインシデントを評価セット化して毎日実行、ノイズを計測、レビューが収束するよう再レビューの回数を制限した。
- 人間が担うのは、作るべきか、高リスクコード、パターンになる設計、証拠の読み取り、結果への責任。

## 具体的な値

数値はすべて記事の値（公開時点、社内運用）。

- 6月から9月に、Claude Code のコードベースへのマージ済み PR は2倍超、差し戻された割合は40%超減った。
- Anthropic のモノレポで、1日にランドする変更は5月の約2,500件から9月の30,000件超へ。Claude Code は別リポジトリ。
- 人間の時間の指標: PR あたりの人間の承認数（中央値と95パーセンタイル）、人間のコメント数、人を待つ時間。
- 研究プレビュー開始時、社内 PR のうち実質的なレビューコメントが付いた割合は16%から54%へ。1,000行超の PR の大半に指摘が付き、小さな PR の大半は指摘なし。
- 公開版 Code Review は Team と Enterprise で GA。`/code-review` はローカルの軽量版。管理者がリポジトリごとに Quick / Standard / Deep を設定する。
- 指摘の検証: 複数エージェントが並列でバグを探し、別のグループが投票して、十分な賛成を得たものだけ投稿する。スタイル、診断、整理のみの指摘は除外（自社 PR で A/B テスト）。インラインコメントは重大度順で、Important / Nit / Pre-existing のタグ付き。全指摘に「修正」か「理由付きで解決」の返答が必要。
- セキュリティレビューは別パス。バグレビューかセキュリティレビューの未解決の指摘があるとマージ不可。後続コミットで直ると指摘は自動で消える。同等のものとして、OSS の security review GitHub Action と `/security-review` を挙げている。
- PR テンプレートは「どうテストしたか」「どう戻すか」を問う（採用案では "Testing"、"Risk"、"How to revert"）。
- リスク別の承認: Low（docs、文言、社内専用機能、フラグ裏の追加的変更）は自動レビューとセキュリティチェックが通れば人間不要 / Medium（通常の製品変更、キャッシュ、auto-updater、システムプロンプトなど）は1人 / High（最高リスクのコードと、常に2人が必要な少数のパス）は2人。
- 分類器は変更内容でティアを決める（著者ではない）。第2の分類器が「ティアが不要でも追加の人が要るか」を判定。所有者が機微と指定したもの、CI ワークフローファイルは常に人が必要。軽い経路は信頼済み著者リストの著者のみ。エージェントの push や手動マージ解決など検証できないコミットが入ると、承認は取り直し。エージェント PR では、エージェントに指示した人が必要レビュアーの1人に数えられる。
- マージキューは最新の main に変更を適用して全チェックを再実行。新機能はフラグの裏で社内先行、公開は latest チャンネルが先で stable が後。
- フラグはデプロイなしで切れる。週次のオンコール。インシデントレビューは「どの層が捕まえるべきだったか」を問う。サーキットブレーカー（指標が動くと承認を厳しくする仕組み）は未整備で、ゼロ人間マージを増やす前に欲しいという声がある。
- インシデントと revert から作った評価セットでレビュアーを毎日採点。変更（プロンプト、ツール、モデル）はスコアが上がれば残し、上がらなければ捨てる。
- コメントへの反応（修正、誤り、意図的、重要でない）でノイズを計測。クリーンな PR にも走らせ、有害な変更につながる誤報の頻度を数える。優先順位は「実バグの検出が第一、レビュー往復の削減が第二」。
- 収束: ある CLI PR は一晩で50回超のレビューと修正を繰り返した。git blame では、指摘の約59%が最初のレビュー時点から存在したコードだった。対策は3回で打ち切り（著者に方針の見直しを求める）、数回後は差分のみ再レビュー、バグの種類を指摘して全箇所を直させる、投稿済み指摘は再掲しない。
- 収束対策の前後（社内 PR）: 1回の修正で通る割合 65%から78%、5回以上かかる割合 8.9%から1.5%、通るまでの平均レビュー回数 2.08から1.32。
- 既存コードへの夜間レビューも実施。
- 採用案: `CLAUDE.md` を短く保つ、フックでフォーマッタと linter を走らせる、`REVIEW.md` に繰り返しの指摘を移す、CODEOWNERS とブランチ保護、承認を新コミットで無効化、一つのリポジトリで AI レビュアーを試してから広げる。
- `REVIEW.md` の良い例: 失敗が何かを書く（docs は "it lies"、config は "it misroutes"）、nit の上限、スキップするパス、ファイルと行の根拠、件数で始まる要約。
